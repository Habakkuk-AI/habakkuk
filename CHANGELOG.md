## [Unreleased]

## [0.3.0] - 2026-11-14

The first public release. This section sums up what Habakkuk does at release.

### Changed

- **The public skills directory is the default registry.** `hk skills search QUERY` and `hk skills install NAME` now work without any setup: names are looked up in your own `skills.registries` first, then in the directory at habakkuk.ai/skills (`https://habakkuk.ai/skills/index.json`). The index is fetched only by `hk skills` and `hk plugins` search, install and update. An install from it is scanned and starts unapproved like any other. `skills.default_registry: "off"` removes it and a URL there replaces it. `hk security -network` lists it. See [Registries](docs/tools/plugins.md#registries).
- **Registry entries must be pinned and hashed.** An entry in any registry index now has to carry `sha256`, the tree hash of its files, and its `source` has to be a GitHub repository or folder at a full 40-character commit or an `https` URL. A branch, a tag, a local path and another registry name are refused, and nothing is installed when the files do not match the hash. The package also has to call itself what the entry is called, so an entry cannot land under another name (`-name` still lets you choose one). If you run your own registry, add `sha256` to every entry and pin every GitHub source to a commit; `hk skills install SOURCE` prints both.
- **An update stays with the registry a package came from.** `hk skills update` and `hk plugins update` look a registry package up in the registry recorded at install and in no other, so a package of the same name in another registry can never replace it. If that registry no longer lists it, or is gone from the config, the update fails and the installed version stays. A registry update that changes `SKILL.md` (or a plugin's manifest, or a `SKILL.md` inside a plugin) clears the approval, so you read the new instructions before they count as approved again.
- **Command turns carry who sent them.** A turn started by a command (`/skill`, a skill's own command, a plugin's prompt command, `/retry`, `/queue`, `/goal`) now records whether the owner or a guest sent it, as an ordinary message does. On a channel open to everyone, the owner's command used to run with a guest's limits.
- **`hk skills` shows more.** The list marks where each skill comes from (`agent`, `shared`, `plugin`, `bundled`) and ends with the skills an agent is not offered and why: turned off, not approved, or missing something they require. A skill that waits for your approval (installed with scripts, brought in from a project, or saved after outside content) hides nothing: the agent uses whatever else has that name, such as the bundled skill, and neither a bundled skill nor `hk skills enable` ever approves it.
- **Commands that take no arguments show help for `-h`.** `hk init -h` used to write a starter config and `hk serve -h` to start serving. Now `init`, `serve`, `channels`, `status`, `models` and `version` print their usage for `-h`, `--help` or `help`, and refuse any other argument.
- **An empty account is named once, in plain words.** When every model in a chain is refused because it's out of credit or its key or login was rejected, the turn stops at once instead of retrying, and the reply says which providers and why ("no model could answer: deepseek is out of credit and anthropic is out of credit"). Later calls keep saying "out of credit" while the keys are set aside, instead of "all credentials cooling down". A schedule or other background work tells each chat once per outage, again only after a day or after a provider has worked and failed again; a message you send always gets the answer. A rate-limited key or a login that couldn't be refreshed is never taken for an outage. A provider with no key or login set says so. Jobs that fail in a way retrying can't fix now count as finished everywhere, so their chat hears about them on the first try. See [Providers](docs/models/providers.md).
- **Scheduled runs ask you instead of failing.** A call that needs approval during a scheduled run used to be denied. Now Habakkuk asks you in the chat the schedule delivers to, says which scheduled task it's for, and waits up to 15 minutes, as any chat does. Saved approval rules never answer for a scheduled run. While a run is still going, the schedule's next slot is skipped, and a chat holds one request at a time for at most the approval timeout. A schedule with no delivery chat, a run on an account open to everyone, and other unattended work (sub-agents, board cards, webhooks, the API) still have nobody to ask. A run that has read outside content always asks a person. See [Approvals in scheduled runs](docs/agents/approvals.md#approvals-in-scheduled-runs).
- **Writes to an agent's instruction files always ask.** `write_file`, `edit_file` and `apply_patch` on a file named `SOUL.md`, `AGENTS.md`, `IDENTITY.md` or `USER.md` (in any case), on the agent's saved approval rules, or on a file with more than one name (a hard link), need your approval in every mode, `full` included, in a trusted notes folder and with a reviewer. No rule covers them, nor a command that names one, however it's quoted. See [Instruction files](docs/agents/approvals.md#instruction-files).
- **Tasks from other agents (A2A) are outside content.** An inbound A2A task now taints its turn, so its risky calls need a person and no approval rule answers for it. See [Security](docs/deploy/security.md#outside-content-taints-a-turn).
- **A streamed reply always starts below the progress line.** On Slack the reply used to be written into the progress message, which could sit above an approval request and didn't notify. It now gets a new message on every platform.
- **Replies show while they're written.** On Telegram and Slack, the reply appears in one message that grows as the model writes it, and that message becomes the reply: no second copy, and still exactly once after a crash. On Telegram the reply gets its own message that notifies and quotes the question, since progress lines are silent. Short lines a model writes before using a tool ("Let me check") don't show. `stream: false` on a channel turns it off, and the setting reloads without a restart.
- **`hk` is the name shown everywhere.** Help, hints, error messages and the docs now write commands as `hk ...`. `habakkuk` is still the program's full name and runs every command. The first-run screen says `habakkuk` only on an install that has no `hk` beside the binary.
- **Chats show one plain line while the agent works.** `progress` on a channel is now `plain` by default: one short line in everyday words, such as "Checking the web" or "Handing this to Ada", edited as the work moves on, with the time after about 20 seconds. It never shows tool names, commands, paths, ids or JSON. The old list of tool steps is `progress: detailed`; `progress: draft` still works and means `detailed`. `off` is unchanged. The lines are in all ten languages (new text is machine-translated and marked for review). The terminal, the terminal UI and the dashboard still show every step. See [channel settings](docs/channels/settings.md#what-a-chat-shows-while-the-agent-works).
- **Approval requests in a chat use plain words.** A request now says what the agent wants to do ("I'd like to add a note to decisions.md in your Bramblecrest Bakery workspace."), why it is asking when there is a reason, and "Reply yes or no". The sentence is derived from the tool call with no model involved. A command is named only when it is one simple step; anything more reads as "run a command", so the line never says less than the command does. The exact command is no longer shown by default: reply `details` to see it (secrets removed, long calls cut short; the request keeps waiting), or set `approvals_detail: full` on the channel to always include it. The local web chat keeps the exact call. See [approval requests](docs/channels/settings.md#approval-requests-in-plain-words).

### Added

- **`hk migrate finish` switches over with one agent running.** Importing from Hermes Agent or OpenClaw left the old agent running, and a worker or service of it could keep firing its own schedules next to the imported ones, so each one ran twice. The import plan and `hk migrate finish` now show what of the old agent still runs: its processes (gateway, workers, scheduler, channel bridges), its services (systemd, launchd, Windows scheduled tasks and Startup launchers), its pid and lock files, its schedules that are on, and each channel both agents would use (the same bot token, or a WhatsApp number still linked in the old agent). Only your own processes that can be tied to the home you're moving from are stopped; one that looks like the old agent but can't be tied to it is listed for you to stop. Once you confirm, `finish` sets Hermes Agent's own pause switch in the home and each profile, stops and disables the old agent's services, stops its worker scopes and leftover processes, pauses its schedules in its own store (paused, never deleted), and resumes the imported schedules that match the ones it ran. It won't resume them while the old scheduler runs or may run, or when it can't see what runs, unless `--force`. Each change is written to `$HABAKKUK_HOME/migrate/cutover-<source>.json` and flushed before it's made, and `hk migrate rollback` undoes it, putting each old schedule and service back exactly as it was. `hk doctor` warns when an old agent runs a schedule that's on in Habakkuk too, or uses one of its channels, and names the fix. A Hermes Agent job carrying its own pause marker is now read as off, so it isn't imported as a running schedule. Hermes Agent's dashboard is found by its own systemd unit and in the form its Python relaunches it, and a worker scope that only holds what a finished worker started is still found and stopped. See [Switch over with hk migrate finish](docs/get-started/migrate.md#switch-over-with-hk-migrate-finish).
- **Skills that come with Habakkuk.** A new install has 33 skills inside the program: a daily brief, inbox triage, meeting prep and notes, research with citations, fact checks, summaries, documents to actions, a weekly review, plain writing, code review, debugging, tests, GitHub through `gh`, Google Workspace through an MCP server, and more. `hk skills` lists them as `bundled`. They are read from the binary, so an update brings the newest ones, and any skill of your own with the same name takes a bundled one's place. `skills.bundled: false` leaves them out. The session prompt lists your own skills first, so the bundled set never crowds them out. See [Skills](docs/agents/skills.md#skills-that-come-with-habakkuk).
- **Every skill is a slash command.** `/daily-brief`, or `/meeting-notes` followed by what to apply it to, runs that skill on every chat app, in `hk chat` and in the terminal UI, as `/skill NAME` does. Habakkuk's own commands and plugins' commands come first, and a skill whose name is a command's (`stop`, `remember`, `usage`) gets no command at all, on any interface: it runs with `/skill NAME`, and `skill_save`, `hk skills install`, `hk skills` and `/skills` say so. `_` works in place of `-`. The terminal UI also gains `/skills`, `/skill`, `/learn` and plugin commands.
- **Turn a skill off without removing it.** `hk skills disable NAME` and `hk skills enable NAME`, or `skills.disabled: [NAME]` in `config.yaml`, for any skill wherever it comes from (bundled, shared, a plugin's or an agent's own). A skill that is off is not in the prompt, cannot be loaded and has no command; its files stay. A running `serve` follows the change from the next session.
- **Skills can say what they need.** A `requires` block in a skill's frontmatter names programs (`bins`), environment variables (`env`) and operating systems (`os`). A skill whose requirements the machine does not meet is not offered to agents, and `hk skills` lists it under "Not offered" with what is missing. The bundled `github` skill needs `gh`.
- **The loop guard stops an agent that goes round in circles.** A turn used to stop only at `max_iterations` (200 model calls), so a model that ran the same failing command again and again kept spending. Now the same failing call (same tool, arguments and error), retried straight away, gets the model a plain warning at the third try and ends the turn at the fifth, with a message telling you why. Waiting doesn't count: a call whose tool actually ran 2 seconds or more (hooks and approval waits not included, also approvals a tool asks for while it runs), such as `sleep 10 && curl ...`, or a round in which every call did. A command that fails at once is a repeat whatever it says. Rounds that only repeat earlier calls with the same results are warned about at 8 and stopped at 12, which leaves room for honest waiting. Set the levels per agent under `loop_guard` (`repeat_warn`, `repeat_stop`, `idle_warn`, `idle_stop`; `-1` turns one off). Each warning and stop fires the new `loop_guard` hook and counts in `habakkuk_loop_guard_total{agent,check,action}`. A resumed turn keeps its counts, and a scheduled run the guard stopped counts as failed, with the whole message sent to its chat and home chat. See [Agents](docs/agents/agents.md#when-an-agent-goes-round-in-circles).
- **`hk doctor --fix`.** Doctor makes the fixes that need no decision from you, prints a `fixed:` line for each, then runs the usual checks: an older `config.yaml` is migrated (the old file is kept), missing folders inside `$HABAKKUK_HOME` are created, files there that other users can read are made owner-only, and a background service that points at a binary that's gone is pointed at this one, with only the program path changed (a timestamped copy goes to `service-backups/`, and the reload command is printed). Keys, logins, unknown keys and anything else outside `$HABAKKUK_HOME` stay as advice. A plain `hk doctor` now checks the service file too and ends with what `--fix` would do. See [Troubleshooting](docs/help/troubleshooting.md).
- **Project instruction files.** When an agent works in a code project (its workspace, a delegated task's worktree, an editor's folder), new sessions read the project's `AGENTS.md`, `CLAUDE.md` and `.cursorrules`, from the git root down. A file is followed as instructions only when you trusted its exact content with `hk projects trust`, which always asks on your terminal (on macOS and Linux opened directly, never through standard input, and only as the foreground job; on Windows the console; you confirm by typing back a random code it prints; a hurdle for scripts, not a guarantee), records only the content it showed, shows exactly the text the agent gets with control and invisible characters made visible (and won't trust a file holding them without `-allow-control`), and records the file and the SHA-256 of its content in `$HABAKKUK_HOME/projects/`. Any change, by anyone, makes a file untrusted again, and nothing is trusted automatically. A trusted file still matches through another letter case, a link, or a git worktree of the same repository (only one whose worktree entry points back to it; a hand-written `.git` file carries no trust). Untrusted files are given to the agent as data in the session's first message, every turn of that session is tainted (commands need your approval), and the memory review treats the session as untrusted. `hk projects list [PATH]` shows what you trusted, or what an agent working in PATH really gets; `hk projects untrust` drops a file or a folder. The record counts only while it's private to you (and `hk doctor --fix` won't tighten one that isn't), and no file tool or file-saving tool can write its folder. Each file is cut at 16 KB and all of them at 32 KB; only regular files are read, opened without following a final link or waiting on a FIFO; a link is followed only to another of these files in the project; and your home folder and `$HABAKKUK_HOME` are never a project root. A schedule or board card made in such a session is tainted, even when you typed the request, so its runs ask before shell commands and writes in any mode. `schedule_pause` resumes a paused schedule only in a clean turn you typed, so a tainted turn can't turn an imported script schedule back on. `project_files: off` turns it off. See [Project instruction files](docs/agents/agents.md#project-instruction-files).
- **Saves stay in the real workspace.** Browser downloads, PDFs and screenshots, generated images and videos, `speak`, files a paired device returns, and chat attachments are saved only inside the workspace once links are followed, so a link in the workspace can't lead a save elsewhere, such as into `$HABAKKUK_HOME`. A paired device's `files.put` never writes into a folder laid out as a Habakkuk home on that device. `hk backup`, the `hk migrate` file copy and `IDENTITY.md` updates write through a new temporary file with a random name, so nothing placed at a fixed name can catch the write.
- **Skills saved after reading outside content are held.** `skill_save` in a turn that read a web page, an email or other outside content, or in a guest's turn, puts the skill in `agents/<name>/skills-held/`, where nothing lists or loads it, until you approve it with `hk skills approve AGENT/NAME`. `hk skills held` lists them. A plain `hk skills approve NAME` still means an installed skill only, so one can't stand in for the other.
- **Notifications from the dashboard.** Turn on Web Push per device from the dashboard's Config page and get a notification when an approval is waiting, when a dashboard chat gets a reply while no dashboard shows it, and when a scheduled task fails, with a switch for each. It's standard Web Push done in Go: the server keeps its VAPID key in `$HABAKKUK_HOME/push/`, encrypts each message for the one browser it's for, and sends it only to the browsers' own push services, with nothing else to install or sign up for. Approval notices name the agent and the kind of action, never the command. Changing the dashboard token forgets every registered device. `http.push_contact` names you to the push services. The API gains `GET`/`POST /api/push`, `PUT`/`DELETE /api/push/{id}` and `POST /api/push/{id}/test`. See [Notifications](docs/interfaces/dashboard.md#notifications).
- **Always allow.** Chat approvals offer **Allow once**, **Always allow** and **Deny** (buttons where the platform has them; reply `yes`, `always` or `no` elsewhere), and the request shows the rule it would save, in full, in a code block. An exec rule is one simple command (a program and plain words: no shell syntax, nothing the shell would expand, no quoted `~`, no leading `=`, no `cd`), run in one folder exactly, with its program pinned to where it was found; it works only where commands run on this computer in bash, sh or dash (not in a sandbox, on Windows, or under another `HABAKKUK_SHELL`), and in a workspace outside Habakkuk's home. A file rule lets `write_file`, `edit_file` or `apply_patch` write inside one folder. A rule answers only for a typed turn, whose whole message is plain text you just sent: a text message in a one-to-one chat on Telegram, WhatsApp (linked device or Cloud API) or the WhatsApp agent channel, a line at the `hk chat` (from a terminal) or TUI prompt, or the dashboard's chat (`/api/chat` included). Every other channel is never typed. TUI `/btw`, skill and plugin prompts, `hk run`, `hk send`, retries, `/goal`, Live mode, voice notes and recordings, `hk talk`, quotes, forwards, inline-bot and template-button messages and attachments aren't typed, and a Live call's transcript in the conversation pauses rules. The turn must also be untainted, carry no chat notes, and follow nothing but your own words since your previous typed message. Schedules, notices, board cards, sub-agents, A2A, the API, MCP clients, editors, groups, webhooks and guests always ask a person. A rule saved in a chat applies in that chat, one saved on this computer applies to messages typed here, and each records who saved it. Rules can also be written in `agents.<name>.allow` (`exact`, a simple command, with an optional `in`, or `tool` and `path`); `command:` patterns are refused for now. Saved rules live in `approvals.json` in the agent's folder, apply across restarts and are changed under a file lock. `hk approvals list` and `hk approvals rm ID` manage them, and the dashboard's Approvals page lists them with a Remove button (`GET /api/approval-rules`, `DELETE /api/approval-rules/{agent}/{id}`). No rule covers a command on the hardline blocklist, anything in Habakkuk's home or its own folders, or a command that names, or reaches through a symlink or hard link, an agent's instruction files, an `approvals.json`, or Habakkuk's `config.yaml`, `.env` and databases; file tools always ask for those too. Schedules and board cards a steered or non-owner turn sets up run tainted, a card run that reads outside content marks its card, and turns that read a script's output or a meeting's notes start tainted. Always allow isn't offered for a command or folder with a backquote or a line break, one over 300 characters, or in an email conversation. See [Always allow](docs/agents/approvals.md#always-allow).
- **`hk migrate` brings your past conversations.** Each conversation with the old agent becomes a read-only session of the agent it belonged to, with its title, its time span and, where the old agent noted it, its channel and chat. Only what you and the agent said comes over, each message once: tool calls, tool results, reasoning, rows the old agent never showed (compaction summaries, notices, watched group chatter, rewound or unsent answers, text for the model only) and the context its gateway added to your messages stay behind. The old agent's databases are read without writing anything beside them. Imported history is untrusted reference material: `session_search` marks its hits as imported and taints a turn whose results include them (also after a restart), the memory review and retros never read it, `/btw` refuses it, the built-in MCP server labels it, and only your own surfaces (terminal, desktop app, web UI, editor) and direct chats count as trusted; reply quotes are taken out. Reading an untrusted memory note or history (`memory_read`, `memory_search`, `memory_history`) now taints the turn too, and that survives a restart. The sessions show in `hk sessions` (marked read-only) and on the dashboard; no message is ever added to them, and retention never prunes them. The plan counts conversations and messages per agent; running again adds only new ones. `--history skip` leaves them behind. Imported sessions are recorded in a new `imported_sessions` table in `transcripts.db` (schema version 5). See [Move from another agent](docs/get-started/migrate.md#your-past-conversations).
- **`hk migrate --from claude-code` and `--from codex`.** Import a coding tool's setup into your main agent: its instruction files (`CLAUDE.md`, `AGENTS.md`) as `AGENTS.md`, its MCP servers (Claude Desktop's too), skills, slash commands and custom prompts as skills, and its memory files as notes (marked untrusted, since each tool wrote them itself). Keys and sign-ins are never copied; the plan names the variables to set. `--project DIR` adds one project: its instructions as an untrusted memory note, only the `.mcp.json` servers you approved for that folder in your own `~/.claude.json` (shown in full in the plan), and its skills. A project's skills and commands come in only from a folder you trusted, as the agent's own skills held until `hk skills approve -agent AGENT NAME` (new); the skills curator and `skill_save` leave held skills alone. From every source, a remote MCP server is never copied as it is, and a local one only when its command is a program name or a path and its arguments are a runner (`npx`, `uvx`, `bunx`, `pipx run`, `uv tool run`) with one package, apart from paths, `${VAR}` references and the flags `-y`, `--yes`, `-q`, `--quiet` and `--stdio`; any other comes along only with `--secrets copy`, its values moved into `.env` variables that `config.yaml` names as `${...}`. An MCP server's command, arguments and URL may now name variables as `${NAME}`. `hk setup` offers these imports too, and when an agent's home is also on the computer, `hk migrate` imports the agent and names the coding tool. From every source, a list of commands or tools the old agent could run without asking (`command_allowlist`, `exec-approvals.json`, `permissions.allow`, Codex's command rules) is named in the plan and never becomes an approval rule: each call asks again until you choose Always allow or add it to `agents.<name>.allow`. See [From Claude Code or Codex](docs/get-started/migrate.md#from-claude-code-or-codex).
- **`hk migrate` brings your files along.** Imported persona files, skills and schedules often name files in the old agent's folder (your notes and reports, the scripts schedules run, their state files), so the new agent kept working inside that folder and it could never be removed. The plan now lists every such folder with its size and how often it is named. `--files copy` copies your own ones into `$HABAKKUK_HOME/files` (`--files-dir` for another place, `--files-max` for the largest file, default 1G) and rewrites the references in everything imported, and inside the copied text files, to name the copies. The old agent's own parts (program, caches, logs, sessions, keys, config) are never copied, and the old folder is only read. The copy keeps modes, times and symlinks, can be stopped and run again, never deletes at the destination, and refuses to start without enough free space. `--files skip` leaves the files; `-y` alone does too and says how to bring them over later, which also fixes an import made before, text you changed since included. The report ends with what still points into the old folder. See [Move from another agent](docs/get-started/migrate.md#your-files-in-the-old-folder).
- **Settings you can flip without a restart.** What a chat shows while the agent works (`progress`) and what approval requests show (`approvals_detail`) can be changed while `serve` runs, from the dashboard's Config page, from the chat itself with `/progress [plain|detailed|off]` and `/approvals [summary|full]` (owner only), with `hk setup channel NAME -progress plain -approvals-detail summary`, or by editing `config.yaml`. Each way edits the file in place (comments kept, `config.yaml.bak` written) and applies from the next message. The API gains `GET /api/channels` and `PUT /api/channels/{account}`.
- **Trusted folders for notes.** `agents.<name>.trusted_write_paths: [~/notes]` lets the file tools save notes in named folders outside the workspace without approval, from a chat and after reading outside content. Commands are not covered. Scripts, programs, executables and hidden files are not written there, symlinks are resolved first, Habakkuk's own folders are never trusted, and your home folder or anything above it is refused. `hk security` lists the folders and flags them on an agent outsiders' content can reach. The trade-off is described in [Security](docs/deploy/security.md#trusted-folders-for-notes).
- **Slack `listen_channels`.** A list of channel ids where every message from an allowed sender is for the bot, with no @mention. Each top-level message starts a thread under it, as a mention does. See [Slack](docs/channels/slack.md#channels-where-no-mention-is-needed).
- **Several Slack apps.** Two `type: slack` channels with different app tokens (one app per workspace) run side by side, each on its own Socket Mode connection, and may go to the same agent. Covered by tests and documented.
- **`hk`, the short name.** The installers add `hk` beside `habakkuk` (a link, or `hk.cmd` on Windows; `--no-hk` / `-NoHk` skips it) and the container image has it too, so `hk chat` is `habakkuk chat`. Another program already called `hk` is never replaced.
- **Remote CLI.** `hk -r NAME COMMAND` runs any command on the Habakkuk on a server, so one `hk` works locally and against the server. `hk remote add NAME ssh://user@host` saves a remote (`-identity`, `-home`, `-bin`); commands go over the system ssh client with every argument quoted, a terminal only when yours is one, and the server's exit code. An `https://` remote with `-token-env` runs `status` and `chat` over the HTTP API. `HABAKKUK_REMOTE` and `hk remote default` pick a remote without `-r`; `-r local` runs here. Commands that change the server's install need `--yes-remote`. Remotes live in `remotes.json` in the user config directory, never with a token. See `docs/interfaces/remote-cli.md`.
- **First run, from install to the first finished task.** `hk` on its own prints one short screen: on a new computer, what Habakkuk is and the one command to run (`hk setup`); once set up, whether `serve` runs and the everyday commands (`hk help` keeps the full list). The installers now end with `hk setup` instead of hand-editing steps. `hk setup` gives a new home the dashboard on loopback (the next free port when 8484 is taken) and memory review, ends with a summary (model and fast model, where you talk, memory, dashboard URL, settings) and three things to try, including a morning brief, and on macOS and Linux can install, start and check the background service in one answer. With `-y` it no longer opens a chat, which had used up the first-chat welcome. It links to each provider's key page and gives fixes when no model is found. The first-chat welcome suggests three things to try, morning brief first. Empty chats in the TUI and the dashboard suggest starters, the dashboard's Overview has a Get started panel, and empty Sessions, Schedules, Memory, Skills and Board pages explain themselves with a one-click message. `doctor` ends every problem with its fix and a clean run with the next step; `status` shows the next schedule and warns when no `serve` will run it; `serve` prints the dashboard address; `run` answers up to 200ms sooner.
- **Durable core.** Every turn is a job with a lease and heartbeat in a SQLite queue; a process killed at any point loses no committed work, and a restart reclaims jobs whose owner died. Interrupted tool calls are repaired, not repeated. Storage is split into `control.db`, `transcripts.db`, `state.db`, `web.db`, `usage.db`, `nodes.db` and content-addressed blobs, with retention on by default.
- **Decision model.** An optional `judge:` (TypeSafe's Jev) makes Habakkuk's own small decisions: which model a message needs, whether a tool call is plainly routine before the reviewer model is asked (never for a turn that read outside content), and whether a chat is worth a memory review. Without a key, or when it is slow, everything works as before.
- **Model routing.** An agent's `fast_model` takes quick messages and chores (titles, summaries, memory review) while `model` takes real work; long tool loops move up to `model` automatically (`routing: auto | fast | smart`, `escalate_after`). `hk setup` pairs each provider's recommended model with its cheaper one.

Each runs under a supervisor with a heartbeat watchdog; pairing codes and allowlists; idempotent turns and resumable deliveries; chat approvals, buttons, reactions, polls and live progress drafts.

A model finds likely causes and proposes skill, memory, `SOUL.md`, config and schedule changes. With `apply: safe`, skill and memory changes are applied at once; the rest wait for `hk retro apply` or `/retro apply`, and config is never edited for you. Every change goes through the memory history and can be undone. Reports go to `agents/<agent>/retros/`, a summary to the home chat, and the next retro checks whether the last changes helped (`retro:` in config, `hk retro`, `/retro`, `GET /api/retros/{agent}`).

### Fixed

- **Handed-off work asks you instead of failing.** A sub-agent's task or a board card has nobody watching it, so a call that needed a person was denied, and a "yes" typed to the agent that handed it the work did nothing. Now it asks in a home chat: the working agent's own, or that of the agent that delegated the task or made the card. The request names the agent and the work. With no home chat anywhere, the denial tells the agent to work inside its workspace or that a home chat would let it ask. With `approvals: reviewer`, the denial says that `reviewer_then_human` lets it ask. See [Approvals in handed-off work](docs/agents/approvals.md#approvals-in-handed-off-work).
- **`search_files` with ripgrep outside a git repository.** When `rg` was installed, a search in a folder that isn't a git repository returned files its `.gitignore` excludes, such as logs and build output. It now skips them, as the built-in search always did.
- **Memory history and quick same-size edits on Linux.** Linux stamps a file's modification time from a coarse clock, so a note rewritten with text of the same length a few milliseconds after a write could keep the same time and size. The history then took it as unchanged: a hand edit went unrecorded, and a change cut short by a crash was dropped instead of recovered. A file written in the last two seconds is now always read.
- **`hk update` when there is no release.** Before the first release, or with pre-releases only, `hk update -check` failed with "HTTP 404 from https://api.github.com/...". It now says there is nothing to update to and exits 0; a plain `hk update` fails with the same plain words.
- **Windows installer and a one-entry PATH.** On an account whose user `PATH` had a single entry, as a clean Windows has, `install.ps1` glued the install folder onto that entry instead of adding it, so `habakkuk` was not found in new terminals and the first entry was broken. The PATH handling is fixed and tested in CI under PowerShell 7 and Windows PowerShell 5.1. An `hk.bat` or `hk.com` beside `habakkuk.exe` now counts as another program too.
- **Install script output.** `install.sh` printed every line of `hk version` inside its "Installed ... to" sentence. It prints the version only, and a mirror URL in `HABAKKUK_DOWNLOAD_URL` may end in a slash. When the install folder is not on your `PATH`, the hint names the file your shell reads (`~/.zshrc` for zsh, the macOS default) instead of always `~/.profile`.
- **Pointers in the generated config.** The comments `hk setup` writes into `config.yaml` named README sections that no longer exist. They name the page on habakkuk.ai/docs.
- **Desktop app license.** The macOS bundle and the Windows version info said "MIT License". Habakkuk is under the Apache License 2.0.
- **A turn stays tainted across a restart.** A turn that had read a web page, an email or other outside content, and was then interrupted by a restart or crash, resumed as if it had read nothing, so commands and writes outside the workspace no longer needed a human (in `full` mode, or with `exec` in `channel_allow`, they ran unasked). A resumed turn now sets its taint again from its own transcript.
- **Approvals survive a restart.** A request that was waiting when `serve` stopped used to be lost, and its buttons did nothing. The resumed turn now asks again when it reaches the same call. A button on the old request answers the new one only when it is for the same call (matched by a hash of agent, session, tool and input carried on the button); otherwise the chat is told the request expired and pointed at the one waiting. A typed yes or no for the old request gets the same notice instead of becoming a new message. On Slack a button press is acknowledged before it is handled, so Slack does not show its "did not respond" warning.
- **A restart after a crash no longer uses up extra attempts.** Each worker pool releases the leases a dead process left behind as it starts. A pool acting on a list it made a moment earlier could expire the lease of a worker that had just taken the job over, so one restart could use two of a job's three attempts and fail it. A lease is now released only while the dead process still holds it.
- **A planned restart does not use up a job's attempt.** Stopping `serve` during a turn left the job's lease to expire, and the resumed run counted as the next attempt, so two deploys during one long task failed it. `serve` now hands running jobs back when it is asked to stop: they resume as soon as it starts, at their old place in line, and that run is not counted. A crash or `kill -9` still counts.
- **`hk doctor` and a running `serve`.** A clean run said "Next: hk serve" while `serve` was still starting or alive but quiet. It now says `serve` is running in those cases too.
- **The dashboard's Get started panel on an install in use.** It showed until hidden by hand. It now goes away once the agent has answered a message, or there is a schedule or a second chat channel. Hide still works.
- **Several channels and the race detector.** Each channel's supervisor goroutine wrote the same shared defaults at start. They are now set once, before the channels start.
- **Imported scripts time out less.** `hk migrate` gives a script schedule ten minutes (or its `@every` interval when shorter) instead of the two-minute default, which an imported inbox sync kept hitting.
- **`hk migrate` brings facts across.** A Hermes Agent home that kept learned facts in `memory_store.db` now gets one note per fact, tagged with its category, beside the `MEMORY.md` entries. Facts that repeat an entry are not doubled.
- **A chat's agent now sees what else was sent to that chat.** A scheduled task's result, another agent's home report or `message_home` post, a background result, a board update and `hk send` used to land in a chat without being in the session that answers it, so a reply such as "yes" or "how did you do that?" was read against the wrong message. Each one is now noted for that chat and shown, labelled with who sent it and when, at the start of the next message there: once, capped in size, and safe across a crash.
- **Quoted replies keep the quote.** When you reply to a specific message on WhatsApp, Telegram, Signal or Discord, the agent now sees `[Replying to <who>: "<text>"]` before what you typed.
- **No invented explanations.** Agents are told to check the chat notes, their recent sessions and schedules when you mention something they cannot find, or to say they do not know.
- **WhatsApp `allow_from` and LIDs.** WhatsApp names many senders by a LID instead of their phone number, so an owner listed by number got a pairing code. The linked device now looks up the phone number behind a LID (and the LID behind a number) in its store, and `allow_from` takes either form: `+1 202 555 0142`, `12025550142@s.whatsapp.net`, `98765432101234` or `98765432101234@lid`.
- **Sending to a WhatsApp number.** `hk send -to whatsapp:+12025550142`, schedule `-to` targets and `home:` values failed with "unknown server". A bare number (with or without `+`) now becomes `<digits>@s.whatsapp.net`; `<digits>@lid` and full JIDs pass through. A target that can never work fails at once instead of being retried 20 times; network errors still retry.
- **WhatsApp credential backups.** A copy was written on every reconnect and followed the process umask. Backups are now owner-only (0600 in a 0700 folder) whatever the umask, taken on connect at most once an hour and daily, and pruned to the five newest plus one a day for a week, never deleting the only good copy. The database snapshots in `hk backup` are owner-only too.
- **Security audit and WhatsApp agents.** A `whatsappagent` channel with `allow_from: "*"` was reported as open to anyone, with a critical for a full-mode agent behind it. A WhatsApp agent only hears from its creator, so it now counts as owner-only.
- **Schedule status.** One-off schedules kept "last status: started" after their run finished. Runs now settle to `done`, `failed: <reason>` or a script's own status, and a one-off that has run lists as `ran once`. `schedules add` names the timezone of the first run and its UTC time, and says when an `at` time was read in the config timezone.
- **Slack direct messages.** Replies to a direct message go to the top level of the chat, even when the user wrote inside a thread.
- **Slow startup.** `hk serve` waited for MCP servers (up to 20 seconds) before any channel connected. MCP servers now connect in the background; a turn that needs one still connecting waits up to 15 seconds, then goes on and the model is told the server is still starting. The log says how long it took to the first channel.
- **`hk status` during startup.** It said "not running" while `serve` was starting. It now says "starting" and what serve waits for, until channels have connected.
