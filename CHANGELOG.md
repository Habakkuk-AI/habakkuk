# Changelog

All notable changes to Habakkuk are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

Version in development: `0.3.0-dev`. No release has been tagged yet; this section summarises what the code does today.

### Changed

- **Scheduled runs ask you instead of failing.** A call that needs approval during a scheduled run used to be denied. Now Habakkuk asks you in the chat the schedule delivers to, says which scheduled task it's for, and waits up to 15 minutes, as any chat does. Saved approval rules never answer for a scheduled run. While a run is still going, the schedule's next slot is skipped, and a chat holds one request at a time for at most the approval timeout. A schedule with no delivery chat, a run on an account open to everyone, and other unattended work (sub-agents, board cards, webhooks, the API) still have nobody to ask. A run that has read outside content always asks a person. See [Approvals in scheduled runs](docs/agents/approvals.md#approvals-in-scheduled-runs).
- **Writes to an agent's instruction files always ask.** `write_file`, `edit_file` and `apply_patch` on a file named `SOUL.md`, `AGENTS.md`, `IDENTITY.md` or `USER.md` (in any case), on the agent's saved approval rules, or on a file with more than one name (a hard link), need your approval in every mode, `full` included, in a trusted notes folder and with a reviewer. No rule covers them, nor a command that names one, however it's quoted.
- **Tasks from other agents (A2A) are outside content.** An inbound A2A task now taints its turn, so its risky calls need a person and no approval rule answers for it. See [Instruction files](docs/agents/approvals.md#instruction-files).
- **`hk` is the name shown everywhere.** Help, hints, error messages and the docs now write commands as `hk ...`. `habakkuk` is still the program's full name and runs every command. The first-run screen says `habakkuk` only on an install that has no `hk` beside the binary.
- **Chats show one plain line while the agent works.** `progress` on a channel is now `plain` by default: one short line in everyday words, such as "Checking the web" or "Handing this to Ada", edited as the work moves on, with the time after about 20 seconds. It never shows tool names, commands, paths, ids or JSON. The old list of tool steps is `progress: detailed`; `progress: draft` still works and means `detailed`. `off` is unchanged. The lines are in all ten languages (new text is machine-translated and marked for review). The terminal, the terminal UI and the dashboard still show every step. See [channel settings](docs/channels/settings.md#what-a-chat-shows-while-the-agent-works).
- **Approval requests in a chat use plain words.** A request now says what the agent wants to do ("I'd like to add a note to decisions.md in your Corner Bakery workspace."), why it is asking when there is a reason, and "Reply yes or no". The sentence is derived from the tool call with no model involved. A command is named only when it is one simple step; anything more reads as "run a command", so the line never says less than the command does. The exact command is no longer shown by default: reply `details` to see it (secrets removed, long calls cut short; the request keeps waiting), or set `approvals_detail: full` on the channel to always include it. The local web chat keeps the exact call. See [approval requests](docs/channels/settings.md#approval-requests-in-plain-words).

### Added

- **Always allow.** Chat approvals offer **Allow once**, **Always allow** and **Deny** (buttons where the platform has them; reply `yes`, `always` or `no` elsewhere), and the request shows the rule it would save, in full, in a code block. An exec rule is one simple command (a program and plain words: no shell syntax, nothing the shell would expand, no quoted `~`, no leading `=`, no `cd`), run in one folder exactly, with its program pinned to where it was found; it works only where commands run on this computer in bash, sh or dash (not in a sandbox, on Windows, or under another `HABAKKUK_SHELL`), and in a workspace outside Habakkuk's home. A file rule lets `write_file`, `edit_file` or `apply_patch` write inside one folder. A rule answers only for a typed turn, whose whole message is plain text you just sent: a text message in a one-to-one chat on Telegram, WhatsApp (linked device or Cloud API) or the WhatsApp agent channel, a line at the `hk chat` (from a terminal) or TUI prompt, or the dashboard's chat (`/api/chat` included). Every other channel is never typed. TUI `/btw`, skill and plugin prompts, `hk run`, `hk send`, retries, `/goal`, Live mode, voice notes and recordings, `hk talk`, quotes, forwards, inline-bot and template-button messages and attachments aren't typed, and a Live call's transcript in the conversation pauses rules. The turn must also be untainted, carry no chat notes, and follow nothing but your own words since your previous typed message. Schedules, notices, board cards, sub-agents, A2A, the API, MCP clients, editors, groups, webhooks and guests always ask a person. A rule saved in a chat applies in that chat, one saved on this computer applies to messages typed here, and each records who saved it. Rules can also be written in `agents.<name>.allow` (`exact`, a simple command, with an optional `in`, or `tool` and `path`); `command:` patterns are refused for now. Saved rules live in `approvals.json` in the agent's folder, apply across restarts and are changed under a file lock. `hk approvals list` and `hk approvals rm ID` manage them, and the dashboard's Approvals page lists them with a Remove button (`GET /api/approval-rules`, `DELETE /api/approval-rules/{agent}/{id}`). No rule covers a command on the hardline blocklist, anything in Habakkuk's home or its own folders, or a command that names, or reaches through a symlink or hard link, an agent's instruction files, an `approvals.json`, or Habakkuk's `config.yaml`, `.env` and databases; file tools always ask for those too. Schedules and board cards a steered or non-owner turn sets up run tainted, a card run that reads outside content marks its card, and turns that read a script's output or a meeting's notes start tainted. Always allow isn't offered for a command or folder with a backquote or a line break, one over 300 characters, or in an email conversation. See [Always allow](docs/agents/approvals.md#always-allow).
- **`hk migrate` brings your files along.** Imported persona files, skills and schedules often name files in the old agent's folder (your notes and reports, the scripts schedules run, their state files), so the new agent kept working inside that folder and it could never be removed. The plan now lists every such folder with its size and how often it is named. `--files copy` copies your own ones into `$HABAKKUK_HOME/files` (`--files-dir` for another place, `--files-max` for the largest file, default 1G) and rewrites the references in everything imported, and inside the copied text files, to name the copies. The old agent's own parts (program, caches, logs, sessions, keys, config) are never copied, and the old folder is only read. The copy keeps modes, times and symlinks, can be stopped and run again, never deletes at the destination, and refuses to start without enough free space. `--files skip` leaves the files; `-y` alone does too and says how to bring them over later, which also fixes an import made before, text you changed since included. The report ends with what still points into the old folder. See [Move from another agent](docs/get-started/migrate.md#your-files-in-the-old-folder).
- **Settings you can flip without a restart.** What a chat shows while the agent works (`progress`) and what approval requests show (`approvals_detail`) can be changed while `serve` runs, from the dashboard's Config page, from the chat itself with `/progress [plain|detailed|off]` and `/approvals [summary|full]` (owner only), with `hk setup channel NAME -progress plain -approvals-detail summary`, or by editing `config.yaml`. Each way edits the file in place (comments kept, `config.yaml.bak` written) and applies from the next message. The API gains `GET /api/channels` and `PUT /api/channels/{account}`.
- **Trusted folders for notes.** `agents.<name>.trusted_write_paths: [~/notes]` lets the file tools save notes in named folders outside the workspace without approval, from a chat and after reading outside content. Commands are not covered. Scripts, programs, executables and hidden files are not written there, symlinks are resolved first, Habakkuk's own folders are never trusted, and your home folder or anything above it is refused. `hk security` lists the folders and flags them on an agent outsiders' content can reach. The trade-off is described in [Security](docs/deploy/security.md#trusted-folders-for-notes).
- **Slack `listen_channels`.** A list of channel ids where every message from an allowed sender is for the bot, with no @mention. Each top-level message starts a thread under it, as a mention does. See [Slack](docs/channels/slack.md#channels-where-no-mention-is-needed).
- **Several Slack apps.** Two `type: slack` channels with different app tokens (one app per workspace) run side by side, each on its own Socket Mode connection, and may go to the same agent. Covered by tests and documented.
- **`hk`, the short name.** The installers add `hk` beside `habakkuk` (a link, or `hk.cmd` on Windows; `--no-hk` / `-NoHk` skips it) and the container image has it too, so `hk chat` is `habakkuk chat`. Another program already called `hk` is never replaced.
- **Remote CLI.** `hk -r NAME COMMAND` runs any command on the Habakkuk on a server, so one `hk` works locally and against the server. `hk remote add NAME ssh://user@host` saves a remote (`-identity`, `-home`, `-bin`); commands go over the system ssh client with every argument quoted, a terminal only when yours is one, and the server's exit code. An `https://` remote with `-token-env` runs `status` and `chat` over the HTTP API. `HABAKKUK_REMOTE` and `hk remote default` pick a remote without `-r`; `-r local` runs here. Commands that change the server's install need `--yes-remote`. Remotes live in `remotes.json` in the user config directory, never with a token. See `docs/interfaces/remote-cli.md`.
- **First run, from install to the first finished task.** `hk` on its own prints one short screen: on a new computer, what Habakkuk is and the one command to run (`hk setup`); once set up, whether `serve` runs and the everyday commands (`hk help` keeps the full list). The installers now end with `hk setup` instead of hand-editing steps. `hk setup` gives a new home the dashboard on loopback (the next free port when 8484 is taken) and memory review, ends with a summary (model and fast model, where you talk, memory, dashboard URL, settings) and three things to try, including a morning brief, and on macOS and Linux can install, start and check the background service in one answer. With `-y` it no longer opens a chat, which had used up the first-chat welcome. It links to each provider's key page and gives fixes when no model is found. The first-chat welcome suggests three things to try, morning brief first. Empty chats in the TUI and the dashboard suggest starters, the dashboard's Overview has a Get started panel, and empty Sessions, Schedules, Memory, Skills and Board pages explain themselves with a one-click message. `doctor` ends every problem with its fix and a clean run with the next step; `status` shows the next schedule and warns when no `serve` will run it; `serve` prints the dashboard address; `run` answers up to 200ms sooner.
- **Durable core.** Every turn is a job with a lease and heartbeat in a SQLite queue; a process killed at any point loses no committed work, and a restart reclaims jobs whose owner died. Interrupted tool calls are repaired, not repeated. Storage is split into `control.db`, `transcripts.db`, `state.db`, `web.db`, `usage.db`, `nodes.db` and content-addressed blobs, with retention on by default.
- **Decision model.** An optional `judge:` (TypeSafe's Jev) makes Habakkuk's own small decisions: which model a message needs, whether a tool call is plainly routine before the reviewer model is asked (never for a turn that read outside content), and whether a chat is worth a memory review. Without a key, or when it is slow, everything works as before.
- **Model routing.** An agent's `fast_model` takes quick messages and chores (titles, summaries, memory review) while `model` takes real work; long tool loops move up to `model` automatically (`routing: auto | fast | smart`, `escalate_after`). `hk setup` pairs each provider's recommended model with its cheaper one.
- **Models.** Providers of type `anthropic`, `openai` (any OpenAI-compatible API), `responses`, `gemini` and `bedrock`; presets for well-known services and local servers; retry with backoff, key rotation and fallback down a model chain; ChatGPT and GitHub Copilot subscription logins; per-session `/model`; token usage and cost in `usage.db` (`hk usage`, `/usage`).
- **Channels.** Telegram, Slack (Socket Mode, many workspaces), WhatsApp as a linked device, WhatsApp agents, WhatsApp Business Cloud API, Discord, Signal, Matrix, email (IMAP and SMTP), SMS (Twilio), Microsoft Teams, Google Chat, iMessage (BlueBubbles), LINE, Mattermost, IRC, ntfy, Messenger, Instagram, Feishu/Lark, DingTalk, WeCom, Zulip, Rocket.Chat, Nextcloud Talk, Twitch and a web chat. Each runs under a supervisor with a heartbeat watchdog; pairing codes and allowlists; idempotent turns and resumable deliveries; chat approvals, buttons, reactions, polls and live progress drafts.
- **Agents.** Several agents with their own `SOUL.md`, `AGENTS.md` and `IDENTITY.md`; a first-chat welcome that lets the user name the agent; permission modes (`read-only`, `ask`, `workspace`, `full`); an LLM approval reviewer; compaction of long sessions; delegation to sub-agents with structured output, git worktrees and background runs; tool search for large tool catalogs; session titles, fork, rewind and export.
- **Tools.** Files, `exec`, `apply_patch`, `search_files`, background processes, Docker and SSH sandboxes, workspace checkpoints with `hk rollback` and `/undo`, a hardline command blocklist and an SSRF guard; a browser toolset over the Chrome DevTools Protocol; a computer toolset (Linux, macOS, per-agent Xvfb); meeting attendance on Google Meet, Zoom and Teams; images, video, documents, web search and speech.
- **Memory and skills.** Markdown memory notes with full-text and optional semantic search, a user profile (`USER.md`), provenance and untrusted marking, background review and nightly consolidation; `SKILL.md` skills with `/skill` and `/learn`; installing skills and plugins from GitHub, URLs, paths and registries with a lock file, a security scan and backups.
- **Retros.** An agent looks back over a period of its own work: failed, retried and interrupted jobs, tool errors, denied approvals, slow turns, model fallbacks, cost, troubled schedules, stalled cards and delegated tasks, failing deliveries, user corrections and memory changes, each citing its source. A model finds likely causes and proposes skill, memory, `SOUL.md`, config and schedule changes. With `apply: safe`, skill and memory changes are applied at once; the rest wait for `hk retro apply` or `/retro apply`, and config is never edited for you. Every change goes through the memory history and can be undone. Reports go to `agents/<agent>/retros/`, a summary to the home chat, and the next retro checks whether the last changes helped (`retro:` in config, `hk retro`, `/retro`, `GET /api/retros/{agent}`).
- **Work.** Schedules (cron, `@every`, one-off) with at-most-once slots and script schedules; a task board shared by agents.
- **Protocols.** MCP client (stdio and Streamable HTTP, OAuth sign-in, a catalog of servers); Habakkuk as an MCP server; Agent2Agent server and client (1.0 and 0.3); Agent Client Protocol for code editors; an OpenAI-compatible API; Home Assistant tools and triggers; device nodes that lend capabilities from other machines and browsers.
- **Interfaces.** The CLI, a full-screen terminal UI, a web dashboard at `/app/` with a JSON API, Live voice mode over WebRTC, `hk talk` for a local voice loop, and Habakkuk Desktop for macOS, Windows and Linux.
- **Operations.** `hk setup`, `doctor`, `status`, `logs`, `security audit`, `expose tailscale`, `backup`, `restore` and `update`; Prometheus metrics, OTLP traces, log rotation with secret redaction, secret managers, hooks, and localized chat and CLI text.
- **Releases.** Static binaries for Linux, macOS and Windows (amd64, arm64) with `SHA256SUMS` and its Ed25519 signature, which `hk update` checks against the key built into the binary; a multi-arch container image on ghcr.io; desktop app builds; and install scripts for macOS, Linux and Windows (`curl -fsSL https://habakkuk.ai/install.sh | sh`).
- **Project.** Contributing guide, code of conduct, security policy, `NOTICE`, Apache License 2.0, trademark policy (`TRADEMARKS.md`), brand guide, issue and pull request templates, Dependabot, a Makefile, and a docs tree under `docs/`.

### Fixed

- **`hk update` when there is no release.** Before the first release, or with pre-releases only, `hk update -check` failed with "HTTP 404 from https://api.github.com/...". It now says there is nothing to update to and exits 0; a plain `hk update` fails with the same plain words.
- **Windows installer and a one-entry PATH.** On an account whose user `PATH` had a single entry, as a clean Windows has, `install.ps1` glued the install folder onto that entry instead of adding it, so `habakkuk` was not found in new terminals and the first entry was broken. The PATH handling is fixed and tested in CI under PowerShell 7 and Windows PowerShell 5.1. An `hk.bat` or `hk.com` beside `habakkuk.exe` now counts as another program too.
- **Install script output.** `install.sh` printed every line of `hk version` inside its "Installed ... to" sentence. It prints the version only, and a mirror URL in `HABAKKUK_DOWNLOAD_URL` may end in a slash. When the install folder is not on your `PATH`, the hint names the file your shell reads (`~/.zshrc` for zsh, the macOS default) instead of always `~/.profile`.
- **Pointers in the generated config.** The comments `hk setup` writes into `config.yaml` named README sections that no longer exist. They name the page on habakkuk.ai/docs.
- **Desktop app license.** The macOS bundle and the Windows version info said "MIT License". Habakkuk is under the Apache License 2.0.
- **A turn stays tainted across a restart.** A turn that had read a web page, an email or other outside content, and was then interrupted by a restart or crash, resumed as if it had read nothing, so commands and writes outside the workspace no longer needed a human (in `full` mode, or with `exec` in `channel_allow`, they ran unasked). A resumed turn now sets its taint again from its own transcript.
- **Approvals survive a restart.** A request that was waiting when `serve` stopped used to be lost, and its buttons did nothing. The resumed turn now asks again when it reaches the same call. A button on the old request answers the new one only when it is for the same call (matched by a hash of agent, session, tool and input carried on the button); otherwise the chat is told the request expired and pointed at the one waiting. A typed yes or no for the old request gets the same notice instead of becoming a new message. On Slack a button press is acknowledged before it is handled, so Slack does not show its "did not respond" warning.
- **A restart after a crash no longer uses up extra attempts.** Each worker pool releases the leases a dead process left behind as it starts. A pool acting on a list it made a moment earlier could expire the lease of a worker that had just taken the job over, so one restart could use two of a job's three attempts and fail it. A lease is now released only while the dead process still holds it.
- **A planned restart does not use up a job's attempt.** Stopping `serve` during a turn left the job's lease to expire, and the resumed run counted as the next attempt, so two deploys during one long task failed it. `serve` now hands running jobs back when it is asked to stop: they resume as soon as it starts, at their old place in line, and that run is not counted. A crash or `kill -9` still counts.
- **`hk doctor` and a running `serve`.** A clean run said "Next: hk serve" while `serve` was still starting or alive but quiet. It now says `serve` is running in those cases too.
- **The dashboard's Get started panel on an install in use.** It showed until hidden by hand. It now goes away once the agent has answered a message, or there is a schedule or a second chat channel. Hide still works.
- **Several channels and the race detector.** Each channel's supervisor goroutine wrote the same shared defaults at start. They are now set once, before the channels start.
- **Imported scripts time out less.** `hk migrate` gives a script schedule ten minutes (or its `@every` interval when shorter) instead of the two-minute default, which an imported inbox sync kept hitting.
- **`hk migrate` brings facts across.** A Hermes Agent home that kept learned facts in `memory_store.db` now gets one note per fact, tagged with its category, beside the `MEMORY.md` entries. Facts that repeat an entry are not doubled.
- **A chat's agent now sees what else was sent to that chat.** A scheduled task's result, another agent's home report or `message_home` post, a background result, a board update and `hk send` used to land in a chat without being in the session that answers it, so a reply such as "yes" or "how did you do that?" was read against the wrong message. Each one is now noted for that chat and shown, labelled with who sent it and when, at the start of the next message there: once, capped in size, and safe across a crash.
- **Quoted replies keep the quote.** When you reply to a specific message on WhatsApp, Telegram, Signal or Discord, the agent now sees `[Replying to <who>: "<text>"]` before what you typed.
- **No invented explanations.** Agents are told to check the chat notes, their recent sessions and schedules when you mention something they cannot find, or to say they do not know.
- **WhatsApp `allow_from` and LIDs.** WhatsApp names many senders by a LID instead of their phone number, so an owner listed by number got a pairing code. The linked device now looks up the phone number behind a LID (and the LID behind a number) in its store, and `allow_from` takes either form: `+1 202 555 0142`, `12025550142@s.whatsapp.net`, `98765432101234` or `98765432101234@lid`.
- **Sending to a WhatsApp number.** `hk send -to whatsapp:+12025550142`, schedule `-to` targets and `home:` values failed with "unknown server". A bare number (with or without `+`) now becomes `<digits>@s.whatsapp.net`; `<digits>@lid` and full JIDs pass through. A target that can never work fails at once instead of being retried 20 times; network errors still retry.
- **WhatsApp credential backups.** A copy was written on every reconnect and followed the process umask. Backups are now owner-only (0600 in a 0700 folder) whatever the umask, taken on connect at most once an hour and daily, and pruned to the five newest plus one a day for a week, never deleting the only good copy. The database snapshots in `hk backup` are owner-only too.
- **Security audit and WhatsApp agents.** A `whatsappagent` channel with `allow_from: "*"` was reported as open to anyone, with a critical for a full-mode agent behind it. A WhatsApp agent only hears from its creator, so it now counts as owner-only.
- **Schedule status.** One-off schedules kept "last status: started" after their run finished. Runs now settle to `done`, `failed: <reason>` or a script's own status, and a one-off that has run lists as `ran once`. `schedules add` names the timezone of the first run and its UTC time, and says when an `at` time was read in the config timezone.
- **Slack direct messages.** Replies to a direct message go to the top level of the chat, even when the user wrote inside a thread.
- **Slow startup.** `hk serve` waited for MCP servers (up to 20 seconds) before any channel connected. MCP servers now connect in the background; a turn that needs one still connecting waits up to 15 seconds, then goes on and the model is told the server is still starting. The log says how long it took to the first channel.
- **`hk status` during startup.** It said "not running" while `serve` was starting. It now says "starting" and what serve waits for, until channels have connected.
